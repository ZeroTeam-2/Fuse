## MODIFIED Requirements

### Requirement: Real-time прогресс через WebSocket
Система SHALL предоставлять real-time обновления прогресса выполнения сценария через WebSocket-соединение по `runId`. Воркер публикует события (`step:start`, `step:done`, `page:required`, `input:required`, `progress`, `run:done`, `run:error`, `run:status`) в комнату запуска; клиент, подписанный на `runId`, получает их немедленно.

Клиентские сокеты подключены к API-процессу, а воркер исполняется отдельным процессом, поэтому события воркера MUST доставляться в API-процесс через межпроцессный канал поверх MongoDB (публикация конвертов воркером, чтение и трансляция в socket.io-комнаты API-процессом). Прямой вызов гейтвея в памяти допустим только для событий, порождаемых самим API-процессом (отмена, сабмит). Канал MUST работать на standalone MongoDB (без требования replica set). Уведомления (`notification:new` в комнату пользователя) доставляются тем же каналом.

Канал доставляет «живость», а не истину: состояние `Run` MUST быть сохранено в MongoDB до публикации события, чтобы потеря события в канале компенсировалась снапшотом. При подключении клиента к `runId` сервер MUST немедленно отправить этому клиенту снапшот текущего состояния `Run` (статус, `currentStep`, накопленные `stepResults`, текст ошибки при наличии) — до и независимо от последующих инкрементальных событий. Клиент, подключившийся после начала исполнения (в том числе после завершения запуска, после реконнекта или перезагрузки страницы), MUST получить актуальное состояние и MUST NOT остаться без обратной связи из-за событий, отправленных до его входа в комнату.

**Поток событий MUST NOT быть единственным источником прогресса.** Живое соединение, по которому ничего не приходит, неотличимо для клиента от «сценарий ещё выполняется», поэтому потерянный поток событий оставляет пользователя в бесконечном «Выполняем сценарий…». Клиент SHALL вести сторож тишины: таймер сбрасывается каждым входящим событием, и если событий не было дольше порога, клиент MUST один раз перечитать состояние запуска (`GET /api/runs/:id`) и применить его теми же правилами, что и снапшот. При продолжающейся тишине интервал MUST расти до потолка, чтобы длинные шаги (задержка, периодический опрос) не превращались в череду запросов. В запуске с нормальным потоком событий сторож MUST NOT сделать ни одного запроса; в фазе ожидания пользовательского ввода тишина ожидаема, и перечитывание MUST NOT затирать уже введённые в форму значения. На терминальной фазе запуска сторож MUST останавливаться.

**Комната запуска MUST быть закрытой.** Имя комнаты — это `runId` из `handshake.query`, то есть значение, которым распоряжается клиент: без проверки на входе любой знающий (или подобравший) `runId` получает снапшот и весь поток событий чужого запуска, включая тела ответов стороннего API. Поэтому соединение SHALL аутентифицироваться при handshake: сервер MUST извлечь JWT access-токен из `handshake.auth.token` либо из cookie `access_token` в `handshake.headers.cookie`, верифицировать его и получить `userId`; при отсутствии или невалидности токена — отклонить соединение с причиной `unauthorized`, не отправляя снапшот. Перед входом в комнату сервер MUST проверить формат `runId` и загрузить `Run`: при `run.userId !== userId` соединение MUST отклоняться с причиной `forbidden`. Тот же инвариант уже действует для канала уведомлений, где комната персональная, — гейтвей запуска MUST использовать тот же способ извлечения и проверки токена.

#### Scenario: Событие воркера доходит до клиента API-процесса
- **WHEN** воркер, исполняющийся отдельным процессом, публикует `step:done` для запуска, на который подписан клиент-владелец, подключённый сокетом к API-процессу
- **THEN** клиент получает событие через WebSocket с задержкой, незаметной пользователю (без ручного обновления страницы)

#### Scenario: Уведомление из воркера доходит до колокольчика
- **WHEN** воркер завершает запуск (или переводит его в `waiting_input`) и создаёт уведомление владельцу
- **THEN** событие `notification:new` доходит через межпроцессный канал до клиента владельца, подключённого к API-процессу, и счётчик колокольчика обновляется без перезагрузки

#### Scenario: Подключение после старта исполнения
- **WHEN** воркер начал (и, возможно, уже завершил) исполнение до того, как клиент-владелец подключился к `runId`
- **THEN** клиент при подключении получает снапшот с текущим статусом и результатами шагов и отображает актуальное состояние вместо бесконечного «Выполняем сценарий…»

#### Scenario: Быстрый запуск завершился до подключения
- **WHEN** запуск падает или завершается за миллисекунды — раньше, чем браузер успел открыть WebSocket
- **THEN** клиент при подключении получает снапшот со статусом `failed` (с текстом ошибки) либо `completed` (с результатами) и показывает соответствующий экран

#### Scenario: Reconnect после обрыва WebSocket
- **WHEN** WebSocket-соединение обрывается во время выполнения
- **THEN** клиент переподключается по `runId`, повторно проходит аутентификацию handshake тем же JWT, получает снапшот текущего статуса и результаты выполненных шагов без потери прогресса

#### Scenario: Кратковременный сбой межпроцессного канала не искажает состояние
- **WHEN** канал доставки событий между воркером и API временно недоступен, пока запуск продолжает исполняться
- **THEN** состояние `Run` в MongoDB продолжает обновляться, и клиент после реконнекта (снапшот) видит актуальные статус и результаты шагов

#### Scenario: Поток событий потерян при живом соединении
- **WHEN** соединение установлено, но события по запуску не приходят (канал доставки моргнул, событие потеряно), а запуск при этом уже завершился
- **THEN** после порога тишины клиент перечитывает состояние запуска, показывает результат и MUST NOT остаться в бесконечном «Выполняем сценарий…»

#### Scenario: Нормальный запуск не порождает лишних запросов
- **WHEN** события `step:start` / `step:done` / `run:done` приходят потоком
- **THEN** сторож тишины сбрасывается каждым событием и не делает ни одного запроса за состоянием

#### Scenario: Подключение без JWT
- **WHEN** клиент подключается к namespace `runs` без cookie `access_token` и без `handshake.auth.token`
- **THEN** сервер немедленно отключает сокет с причиной `unauthorized`, снапшот не отправляется и вход в комнату не выполняется

#### Scenario: Подключение к чужому запуску
- **WHEN** аутентифицированный пользователь подключается с `runId`, у которого `run.userId` не совпадает с `userId` из токена
- **THEN** сервер отключает сокет с причиной `forbidden`, не отправляет снапшот и не добавляет сокет в комнату — последующие события запуска до него не доходят

### Requirement: Движок исполнения шагов
Worker SHALL исполнять шаги сценария последовательно: для каждого шага разрешать входы по маппингу (выходы предыдущих шагов, ввод пользователя, константы, включая подстановку `{{token}}`-шаблонов), выполнять HTTP-вызов endpoint стороннего API и сохранять ответ как выходы шага в документ `Run`.

Пользовательский ввод MUST быть доступен **каждому** шагу запуска, а не только первому: worker MUST засеивать ввод шага значениями, собранными перед запуском (`Run.inputs`, срез по пути шага), и переносить накопленный ввод от шага к шагу. Шаг «Другой сценарий» MUST получать срез входов, адресованных его вложенным шагам.

Для шагов, привязанных к приложению (`api`, `periodic`, `file`), worker MUST разрешать **абсолютный URL** вызова: загружать `App` по `appId` шага и склеивать `App.baseUrl` с путём шага (`path` / `pollPath` / `uploadPath`). Относительный путь шага MUST NOT передаваться в HTTP-клиент напрямую. Если приложение не найдено либо у него не задан `baseUrl`, шаг MUST завершаться доменной ошибкой с диагностикой, указывающей на приложение и на необходимость переимпорта спецификации.

Резолвнутый URL MUST проходить проверку SSRF перед вызовом, и проверка MUST быть устойчива к обходам. Классификация адреса MUST выполняться библиотечным разбором IP (RFC 6890), а не списком регулярных выражений: под запрет попадают loopback, частные диапазоны, link-local вместе с `169.254.169.254`, ULA `fc00::/7`, CGNAT `100.64.0.0/10`, multicast и IPv4-mapped IPv6 (`::ffff:127.0.0.1`), а также decimal-, octal- и hex-записи IPv4. Между проверкой и соединением MUST NOT быть окна для подмены адреса: имя резолвится один раз, полученный IP валидируется и **пиннится** на соединение (кастомный `lookup` диспетчера), иначе DNS rebinding сводит проверку на нет. Редиректы MUST обрабатываться явно: каждый `Location` проходит ту же проверку, а не следуется автоматически.

Список исключений `SSRF_ALLOWED_HOSTS` существует только для локальной разработки (сценарии бьют по мок-API на `localhost`) и обходит и блок-лист, и резолв DNS. Поэтому непустое значение при `NODE_ENV=production` MUST приводить к отказу приложения стартовать — так же, как это уже сделано для пароля локального входа.

Ответ API-шага worker MUST сохранять по типу содержимого: `application/json` — как распарсенный JSON в `stepResults[i].result`; `text/*` — как строку; иное (файловое содержимое, а также ответы с `Content-Disposition: attachment`) — бинарно в S3 как артефакт запуска, записывая в `stepResults[i].result` файловую ссылку (`RunFileRef`) и регистрируя объект в реестре файлов запуска. Сырое бинарное тело MUST NOT записываться в Mongo.

Шаг «Задержка» MUST приостанавливать поток на заданное время; «Периодический запрос» MUST опрашивать endpoint с интервалом до признака завершения, публикуя прогресс; «Другой сценарий» MUST исполнять вложенный сценарий как один шаг. Ошибка шага MUST переводить `Run` в статус `failed` с диагностикой (шаг, endpoint, статус ответа). Тело ответа стороннего API MUST обрезаться перед записью в `stepResults[].error` и `run.error` — полный текст остаётся только в server-side логах (см. capability `audit-logging-sanitization`).

Запись результатов шагов MUST быть идемпотентной: повторная обработка одного и того же `runId` (повторная доставка сообщения очереди) MUST NOT создавать дублирующиеся записи `stepResults` с одинаковым `stepIndex` и MUST NOT переводить `Run` из терминального статуса (`completed`, `failed`, `cancelled`) обратно в незавершённый. Worker SHALL валидировать `runId` из тела SQS-сообщения как ObjectId до обращения к базе: невалидное сообщение MUST подтверждаться с записью в лог, а не уходить в бесконечный цикл повторных доставок на ошибке приведения типа.

При переводе `Run` в терминальный статус, а также в `waiting_input`, worker MUST инициировать создание уведомления владельцу запуска (см. capability `run-notifications`).

#### Scenario: Резолв базового URL приложения
- **WHEN** worker исполняет `api`-шаг с `path: "/collections"` у приложения с `baseUrl: "https://dadata-fake.cloud.astral-dev.ru"`
- **THEN** worker вызывает `https://dadata-fake.cloud.astral-dev.ru/collections` и сохраняет тело ответа как результат шага

#### Scenario: Base path приложения сохраняется
- **WHEN** у приложения `baseUrl: "https://api.example.com/v1"`, а путь шага — `/collections`
- **THEN** worker вызывает `https://api.example.com/v1/collections`

#### Scenario: У приложения не задан базовый URL
- **WHEN** worker исполняет шаг приложения, у которого `baseUrl` пуст
- **THEN** шаг завершается ошибкой с сообщением, называющим приложение и предлагающим переимпортировать спецификацию, а `Run` переходит в `failed` — без низкоуровневой ошибки разбора URL

#### Scenario: SSRF block на metadata endpoint
- **WHEN** приложение настроено с `baseUrl: "http://169.254.169.254"`, либо тот же адрес приходит в decimal-записи (`http://2852039166`)
- **THEN** worker отклоняет вызов до установления соединения, шаг завершается как `failed`, и ответ metadata-сервиса не попадает в результаты запуска

#### Scenario: DNS rebinding отклонён
- **WHEN** DNS отдаёт публичный адрес в момент проверки и приватный — в момент соединения
- **THEN** соединение идёт на проверенный (запиннённый) IP, подмена не срабатывает, и шаг завершается как `failed`, если проверенный адрес недоступен

#### Scenario: Редирект на приватный адрес отклонён
- **WHEN** публичный endpoint отвечает `302 Location: http://127.0.0.1:3001/api/users/me`
- **THEN** worker не следует редиректу автоматически, прогоняет адрес назначения через ту же проверку и завершает шаг ошибкой

#### Scenario: Непустой SSRF_ALLOWED_HOSTS в production
- **WHEN** приложение (API или воркер) стартует с `NODE_ENV=production` и непустым `SSRF_ALLOWED_HOSTS`
- **THEN** валидация конфигурации падает на старте с сообщением о том, что список исключений допустим только вне production

#### Scenario: Подстановка шаблона в константе
- **WHEN** константа шага содержит `Bearer {{access_token}}` и предыдущий шаг вернул `access_token`
- **THEN** worker подставляет значение токена в заголовок Authorization перед HTTP-вызовом

#### Scenario: Пользовательский ввод доступен на всех шагах
- **WHEN** пользователь ввёл значения в форме перед запуском, а ручной ввод помечен у параметров шага 1 и шага 3
- **THEN** шаг 3 видит накопленный пользовательский ввод и разрешает свой `user`-источник из него, а не получает пустое значение

#### Scenario: Периодический опрос до завершения
- **WHEN** шаг «Периодический запрос» опрашивает endpoint каждые 5 сек до признака завершения в ответе
- **THEN** worker публикует прогресс (значение поля прогресса) на каждой итерации и завершает шаг при получении признака завершения

#### Scenario: Файловый ответ API уходит в S3
- **WHEN** api-шаг (или финальный запрос periodic-шага) возвращает `Content-Type: application/zip`
- **THEN** worker сохраняет тело в S3, в `stepResults[i].result` попадает `RunFileRef`, объект регистрируется в реестре файлов запуска, а бинарное тело в Mongo не пишется

#### Scenario: Повторная доставка сообщения не дублирует результаты
- **WHEN** сообщение с одним и тем же `runId` доставляется worker'у повторно
- **THEN** результаты шагов перезаписываются по индексу, дубликаты `stepResults` не появляются, а уже терминальный `Run` не возвращается в `running` или `waiting_input`

#### Scenario: Доменная ошибка шага не уходит на повторную доставку
- **WHEN** шаг падает детерминированно (недоступный endpoint, ошибка стороннего API)
- **THEN** worker фиксирует `failed` в `Run`, публикует ошибку и подтверждает сообщение очереди — повторные доставки того же детерминированного сбоя не выполняются

#### Scenario: Невалидный runId в SQS-сообщении
- **WHEN** worker получает сообщение с телом `{ "runId": "not-an-objectid" }`
- **THEN** сообщение отбраковывается до обращения к базе, подтверждается очереди с записью в лог и не уходит в цикл повторных доставок на ошибке приведения типа

## ADDED Requirements

### Requirement: Проверка владельца на state-changing эндпоинтах выполнения
Все эндпоинты управления запуском (`GET /api/runs/:id`, `GET /api/runs/:id/file-link`, `POST /api/runs/:id/cancel`, `POST /api/runs/:id/page-submit`, `POST /api/runs/:id/input-submit`, `DELETE /api/runs/:id`) SHALL принимать `userId` из JWT и проверять, что `run.userId === userId`, в сервисном слое — а не в контроллере и не отдельным guard'ом на каждый маршрут. При несовпадении система MUST отвечать `403 Forbidden` и не изменять документ.

Требование фиксирует уже действующий в коде инвариант, чтобы он не был потерян при следующем расширении API: новый эндпоинт, принимающий `runId`, MUST проходить ту же проверку.

#### Scenario: Владелец отменяет свой запуск
- **WHEN** аутентифицированный пользователь отправляет `POST /api/runs/<свой-run-id>/cancel`
- **THEN** система проверяет владельца, отменяет запуск и возвращает обновлённый документ `Run`

#### Scenario: IDOR-попытка отменить чужой запуск
- **WHEN** аутентифицированный пользователь отправляет `POST /api/runs/<чужой-run-id>/cancel`
- **THEN** система отвечает `403 Forbidden` и не меняет статус запуска

#### Scenario: IDOR-попытка инъекции данных в чужой запуск
- **WHEN** аутентифицированный пользователь отправляет `POST /api/runs/<чужой-run-id>/page-submit` с произвольным телом
- **THEN** система отвечает `403 Forbidden` и не модифицирует `stepResults` или `inputs` чужого запуска
