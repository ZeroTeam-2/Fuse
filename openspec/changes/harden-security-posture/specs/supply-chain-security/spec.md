## ADDED Requirements

### Requirement: Поиск секретов в пайплайне
Пайплайн SHALL искать секреты в изменениях на каждый merge request и падать при находке. Прецедент уже есть: артефакты change'а приехали в публичный репозиторий с боевым паролем базы и OAuth-секретом открытым текстом, пролежали там почти четыре месяца, и ни один автоматический гейт этого не заметил.

Требование не привязано к конкретной платформе CI: проект уезжает с GitHub Actions на GitLab CI, и гейт переносится вместе с остальными проверками.

#### Scenario: Секрет в изменениях
- **WHEN** в merge request попадает ключ или пароль, распознаваемый сканером
- **THEN** проверка падает с указанием файла и строки, изменения не вливаются

#### Scenario: Изменения без секретов
- **WHEN** секретов в изменениях нет
- **THEN** проверка проходит

### Requirement: Гейт по уязвимостям зависимостей
Пайплайн SHALL запускать аудит production-зависимостей на каждый merge request и падать при уязвимостях высокого и критического уровня.

#### Scenario: Уязвимая зависимость
- **WHEN** в локфайле появляется production-зависимость с уязвимостью высокого уровня
- **THEN** проверка падает с описанием и путём обновления

### Requirement: Сканирование образов
Пайплайн SHALL сканировать собираемые образы на известные уязвимости и падать при критических. Базовые образы (`node:24-alpine`, `caddy:2-alpine`) обновляются вне репозитория, и без сканирования о протухшем базовом слое никто не узнаёт.

#### Scenario: Критическая уязвимость в образе
- **WHEN** собранный образ содержит пакет с критической уязвимостью
- **THEN** проверка падает с указанием пакета и слоя

### Requirement: Принудительные версии транзитивных зависимостей
Корневой `package.json` SHALL фиксировать через `pnpm.overrides` минимальные версии пакетов, которые тянутся транзитивно и имеют известные уязвимости.

Прямые зависимости уже в порядке: backend объявляет `multer@^2.2.0`, в локе есть `tar@7.5.19`. Проблема в транзитивных: `multer@2.1.1` приходит из `@nestjs/platform-express`, `tar@6.2.1` — из цепочки сборки. Override нужен именно для них.

#### Scenario: Транзитивная версия поднята
- **WHEN** выполняется установка зависимостей
- **THEN** в локфайле не остаётся `multer` ниже 2.2.0, включая транзитивные вхождения

### Requirement: Неиспользуемая автоматизация удаляется, а не укрепляется
Автоматизация, которой больше никто не пользуется, SHALL удаляться вместе с её секретами — вместо того чтобы чинить в ней уязвимости.

Конкретно: `change-bootstrap.yml` и `change-complete.yml` реализуют change-флоу на GitHub Actions, который заброшен, а проект переезжает на GitLab CI. В них сразу три дефекта — долгоживущий PAT `FLOW_TOKEN` с правами на issues и pull requests, подстановка `${{ steps.change.outputs.id }}` прямо в текст shell-команды (имена git-веток допускают `;`, `$`, `(`, `)` и обратные кавычки, то есть ветка с метасимволами выполняет произвольный код в раннере) и отсутствие ограничения на PR из форков. Удаление обоих файлов и отзыв токена закрывают все три разом и не оставляют кода, который надо сопровождать.

Токен MUST отзываться у провайдера, а не только удаляться из секретов репозитория: удаление секрета оставляет PAT действующим.

#### Scenario: Заброшенная автоматизация удалена
- **WHEN** проверяется содержимое каталога workflow'ов
- **THEN** файлов change-флоу в нём нет, и ни один оставшийся пайплайн не ссылается на `FLOW_TOKEN`

#### Scenario: Токен отозван, а не просто скрыт
- **WHEN** проверяется список персональных токенов аккаунта
- **THEN** `FLOW_TOKEN` в нём отсутствует — попытка воспользоваться им получает отказ

### Requirement: Явные минимальные права пайплайна
Каждая оставшаяся конфигурация CI SHALL объявлять минимально необходимые права. В `spec-gate.yml` блок `permissions` уже есть; в `ci.yml` его нет, и job работает с правами по умолчанию для репозитория. При переносе на другую платформу то же правило применяется к её механизму прав.

#### Scenario: Пайплайн с минимальными правами
- **WHEN** проверяется конфигурация пайплайна, которому нужен только исходный код
- **THEN** в ней объявлены права не шире чтения репозитория

### Requirement: Шаги пайплайна закреплены по версии
Сторонние шаги SHALL закрепляться по неизменяемой ссылке (commit SHA для GitHub Actions, тег образа с digest для GitLab CI), а не по подвижному тегу. Сейчас везде стоят подвижные теги (`actions/checkout@v4`, `pnpm/action-setup@v4`, `actions/setup-node@v4`): тег переставляется владельцем в любой момент, и содержимое шага меняется без изменения репозитория.

#### Scenario: Шаги закреплены
- **WHEN** проверяются ссылки на сторонние шаги в конфигурации пайплайна
- **THEN** каждая указывает неизменяемую версию с комментарием, какой релиз ей соответствует
