## ADDED Requirements

### Requirement: Глобальный фильтр исключений
Система SHALL регистрировать глобальный фильтр исключений через `APP_FILTER`. Для `HttpException` фильтр отдаёт исходный статус и сообщение. Для любой другой ошибки фильтр записывает stack в server-side лог и отвечает клиенту `500` с телом без stack, без сообщения исходной ошибки и без путей файловой системы — только статус и идентификатор запроса, по которому сопровождение найдёт запись в логе.

Без такого фильтра наружу уходят тексты, которых клиент не должен видеть: сообщения драйвера MongoDB с частями строки подключения, ошибки S3-клиента с именем бакета и endpoint'ом, тела ответов стороннего API.

#### Scenario: Необработанное исключение
- **WHEN** в обработчике запроса выбрасывается не-`HttpException` (например, `CastError` от Mongoose)
- **THEN** клиент получает `500` с идентификатором запроса и без диагностики, а в server-side логе появляется stack с тем же идентификатором

#### Scenario: HttpException прокидывается
- **WHEN** контроллер выбрасывает `NotFoundException("Scenario not found")`
- **THEN** клиент получает `404` с исходным сообщением — поведение существующих обработчиков не меняется

### Requirement: Идентификатор запроса в логах и ответе
Каждый HTTP-запрос SHALL получать идентификатор, доступный и логам, и ответу (`x-request-id`). Идентификатор MUST прокидываться в логи обработки запроса — через `AsyncLocalStorage`, а не прокидыванием параметра по цепочке вызовов. Входящий `x-request-id` SHOULD использоваться как есть, если проходит проверку формата, иначе генерируется новый.

#### Scenario: Ответ содержит идентификатор запроса
- **WHEN** клиент делает запрос без заголовка `x-request-id`
- **THEN** ответ содержит `x-request-id` со сгенерированным значением

#### Scenario: Логи и ответ сходятся по идентификатору
- **WHEN** запрос завершается ошибкой `500`
- **THEN** строки лога этого запроса несут тот же идентификатор, что вернулся клиенту, — по нему запись находится без поиска по времени

### Requirement: Маскирование чувствительных значений в логах
Логи SHALL маскировать значения, по которым можно войти или идентифицировать человека: email, поля с именами `password`, `secret`, `token`, `refreshToken`, `accessToken`, и строки, похожие на JWT. Маскирование MUST применяться там, где логи фактически пишутся.

Сейчас `LoggingService` в приложении не подключён: ни `app.useLogger()`, ни инъекции в сервисы нет, вся запись идёт через `Logger` из `@nestjs/common`. Поэтому redactor внутри `LoggingService` сам по себе ничего не закроет — сервис MUST быть подключён как логгер приложения, иначе маскирование надо делать там, где пишет `Logger`. Это тем важнее, что при заданном `LOG_COLLECTOR_URL` записи уходят на внешний приёмник.

#### Scenario: Email в логе
- **WHEN** в запись лога попадает адрес `user@example.com`
- **THEN** в вышедшей строке адрес замаскирован и не восстанавливается из неё

#### Scenario: Токен в логе
- **WHEN** в запись лога попадает поле с access- или refresh-токеном
- **THEN** значение заменено маркером, и ни одна часть токена в строку не попадает

### Requirement: Обрезка тел ответов стороннего API перед записью в базу
Текст ошибки стороннего API SHALL обрезаться перед сохранением в документ запуска (`stepResults[].error`, `run.error`). Полный текст MUST оставаться только в server-side логе.

Поле `error` показывается в интерфейсе запуска и уходит в снапшот WebSocket, поэтому страница ошибки провайдера целиком — вместе с внутренними адресами, заголовками и иногда ключами — сейчас доезжает до клиента и сохраняется в базе.

#### Scenario: Длинное тело ошибки
- **WHEN** сторонний API отвечает ошибкой с телом в несколько килобайт
- **THEN** в документ запуска попадает обрезанный фрагмент фиксированной длины, а полный текст есть только в логе с идентификатором запроса
