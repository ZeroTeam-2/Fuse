## ADDED Requirements

### Requirement: Глобальный лимит частоты запросов
Система SHALL применять ограничение частоты ко всем входящим HTTP-запросам глобальным guard'ом. При превышении окна система MUST отвечать `429` с заголовком `Retry-After`.

Ключ лимита MUST быть адресом реального клиента. Приложение работает за Caddy, и без доверия к `X-Forwarded-For` (`trust proxy` у Express) `req.ip` равен адресу контейнера прокси — один и тот же для всех пользователей. В таком виде глобальный лимит складывает трафик всех пользователей в один счётчик: сначала он бесполезен как защита, а при росте нагрузки выключает сервис целиком. Поэтому `trust proxy` MUST быть включён с числом доверенных хопов, соответствующим схеме развёртывания, а Caddy MUST проставлять `X-Forwarded-For`.

Health-check контейнеров (`GET /`) ходит с того же адреса каждые 15 секунд и MUST NOT попадать под лимит — иначе оркестратор перезапустит здоровый контейнер.

#### Scenario: Превышение дефолтного лимита
- **WHEN** один клиент превышает дефолтное окно запросов
- **THEN** последующие запросы получают `429` с `Retry-After`, а другие клиенты не затронуты

#### Scenario: Два пользователя за одним прокси
- **WHEN** два пользователя с разных адресов работают одновременно через Caddy, и один из них упирается в лимит
- **THEN** второй продолжает работать — счётчики раздельные

#### Scenario: Health-check не попадает под лимит
- **WHEN** docker healthcheck опрашивает `GET /` с интервалом 15 секунд круглосуточно
- **THEN** ответы остаются `200`, контейнер не помечается unhealthy

### Requirement: Строгие лимиты на аутентификацию
Система SHALL применять отдельный строгий лимит к `/api/auth/callback`, `/api/auth/refresh`, `/api/auth/dev-login` и `/api/auth/logout`. `dev-login` сверяет пару логин-пароль и без лимита перебирается, `refresh` — единственная точка обмена украденного токена на новую пару.

#### Scenario: Перебор на refresh
- **WHEN** клиент превышает строгое окно на `/api/auth/refresh`
- **THEN** последующие запросы получают `429` до истечения окна

#### Scenario: Перебор на локальном входе
- **WHEN** клиент превышает строгое окно на `/api/auth/dev-login`
- **THEN** последующие попытки получают `429`, и перебор пароля не продолжается

### Requirement: Лимиты на публичные эндпоинты маркетплейса
Система SHALL применять лимит к публичным маршрутам маркетплейса (каталог, счётчики категорий, карточка, ручные входы карточки) — это единственные эндпоинты, доступные без аутентификации, и каждый из них делает запрос в базу с пользовательским фильтром.

#### Scenario: Скрейпинг каталога
- **WHEN** неаутентифицированный клиент превышает окно запросов к каталогу
- **THEN** система отвечает `429` и не выполняет запрос к базе

### Requirement: Лимиты на загрузку файлов
Система SHALL применять лимит к `/api/uploads/*`, `/api/users/me/avatar` и к эндпоинтам загрузки спецификаций приложения. Каждый такой запрос буферизует тело в память процесса, поэтому частота здесь ограничивает не трафик, а потребление памяти.

#### Scenario: Множественные загрузки
- **WHEN** аутентифицированный пользователь превышает окно загрузок
- **THEN** последующие запросы на загрузку получают `429`

### Requirement: Хранилище счётчиков под масштабирование
Система SHALL по умолчанию использовать счётчики в памяти процесса и допускать переключение на внешнее хранилище конфигурацией.

Требование существенно: API масштабируется (а воркеры уже запускаются репликами `--scale worker=N`), и счётчики в памяти у N инстансов дают фактический лимит в N раз больше заявленного. Пока API разворачивается одним инстансом, памяти достаточно; выбор внешнего хранилища MUST быть сделан до горизонтального масштабирования API, а не после.

#### Scenario: Один инстанс API
- **WHEN** внешнее хранилище не сконфигурировано
- **THEN** лимиты работают на счётчиках в памяти, без дополнительной инфраструктуры

#### Scenario: Несколько инстансов API
- **WHEN** сконфигурировано внешнее хранилище
- **THEN** счётчики общие для всех инстансов, и заявленный лимит соблюдается суммарно
