## ADDED Requirements

### Requirement: Строгий режим включается по адресатам конфигурации
Валидация окружения SHALL определять «строгий режим» по тому, **на что указывает конфигурация**, а не по значению `NODE_ENV`. Конфигурация считается внешней, если хост в `MONGODB_URL`, `AWS_ENDPOINT_URL`, `AWS_SQS_QUEUE_URL` или `S3_URL` — публичный IP-литерал либо доменное имя с точкой вне `localhost` и `.local`. Односегментные имена (`mongo`, `localstack`, `garage` — сервисы compose), приватные диапазоны и `host.docker.internal` считаются локальными. Строгий режим включается при внешней конфигурации **или** при `NODE_ENV=production`.

Привязка только к `NODE_ENV` не работает, и это проверено на этом проекте: в общем `.env` стояло `NODE_ENV=development`, а `MONGODB_URL` смотрел на внешний сервер, очередь — на Yandex Cloud, хранилище — на Timeweb, при непустом `SSRF_ALLOWED_HOSTS` и включённом локальном входе по паролю. Ни одна проверка, обусловленная production, в таком профиле не сработала бы — а защищать надо было именно его.

#### Scenario: Локальный профиль не ужесточается
- **WHEN** приложение стартует с профилем разработчика (Mongo, LocalStack и Garage на localhost, дефолтные креды контейнеров)
- **THEN** строгий режим не включается, приложение стартует как прежде

#### Scenario: Внешний адрес включает строгий режим
- **WHEN** приложение стартует с `NODE_ENV=development`, но `MONGODB_URL` указывает на внешний хост
- **THEN** строгий режим включается, и профиль проверяется так же, как production

### Requirement: Отказ стартовать с незаполненными и отозванными секретами
В строгом режиме валидация SHALL отклонять пустые значения, документированные плейсхолдеры и отозванные значения для `JWT_SECRET`, `NUXT_SESSION_SECRET`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`. Проверка применяется к обеим схемам: backend (`apps/backend/src/config/env.schema.ts`) и frontend (`apps/frontend/config/env.schema.ts`).

Список отозванных значений MUST храниться как хэши: внести сам секрет в схему значило бы вернуть его в репозиторий тем же действием, которым его оттуда убирают.

#### Scenario: Плейсхолдер в строгом режиме
- **WHEN** приложение стартует в строгом режиме с `JWT_SECRET`, равным значению из `.env.example`
- **THEN** процесс падает на старте с сообщением, называющим переменную и способ сгенерировать значение

#### Scenario: Отозванное значение
- **WHEN** приложение стартует с секретом, хэш которого есть в списке отозванных
- **THEN** процесс падает на старте с явным указанием, что значение скомпрометировано и требует ротации

### Requirement: Опасные для боя переключатели запрещены в строгом режиме
В строгом режиме валидация SHALL отклонять непустой `SSRF_ALLOWED_HOSTS` и непустой `DEV_LOGIN_PASSWORD`.

`SSRF_ALLOWED_HOSTS` обходит и блок-лист хостов, и шаг резолва DNS целиком — одна переменная окружения выключает всю защиту от SSRF, и в примере окружения она заполнена. `DEV_LOGIN_PASSWORD` открывает вход по паролю; сейчас он запрещён только при `NODE_ENV=production`, то есть ровно в том профиле, которого у проекта нет.

#### Scenario: Список исключений SSRF при внешней конфигурации
- **WHEN** приложение стартует в строгом режиме с непустым `SSRF_ALLOWED_HOSTS`
- **THEN** валидация падает с сообщением, что список допустим только в локальном профиле

#### Scenario: Локальный вход при внешней конфигурации
- **WHEN** приложение стартует в строгом режиме с непустым `DEV_LOGIN_PASSWORD`
- **THEN** валидация падает — вход по паролю не поднимается вместе с внешней базой

### Requirement: Качество и независимость секретов подписи
Валидация SHALL требовать от `JWT_SECRET` минимальную длину (уже есть: 32 символа), отклонять вырожденные значения с малым числом различных символов и отклонять совпадение `JWT_SECRET` с `NUXT_SESSION_SECRET`.

Последнее — не гипотетика: до ротации в `.env` это было одно и то же значение, то есть компрометация секрета сессии Nuxt давала возможность подписывать токены доступа.

#### Scenario: Вырожденное значение
- **WHEN** `JWT_SECRET` состоит из одного повторяющегося символа нужной длины
- **THEN** процесс падает на старте с сообщением о недостаточном качестве значения

#### Scenario: Один секрет на две роли
- **WHEN** `JWT_SECRET` и `NUXT_SESSION_SECRET` равны
- **THEN** процесс падает на старте с требованием задать разные значения

### Requirement: Отсутствие фолбэков секрета в коде
Все обращения к `JWT_SECRET` SHALL использовать `getOrThrow`. Фолбэк `?? "fallback"` MUST быть удалён из всех мест.

Сейчас он стоит в четырёх: `app.module.ts`, `auth/auth.module.ts`, `auth/strategies/jwt.strategy.ts` и `auth/yandex-auth.service.ts` (проверка refresh-токена). Это не теоретическая проблема: при незаданном `JWT_SECRET` приложение не падает, а начинает подписывать и принимать токены, подписанные строкой `fallback`, — подделать сессию может кто угодно.

#### Scenario: Фолбэков не осталось
- **WHEN** в `apps/backend/src` ищется литерал фолбэк-секрета
- **THEN** совпадений нет

#### Scenario: Незаданный секрет роняет приложение
- **WHEN** приложение стартует без `JWT_SECRET`
- **THEN** процесс падает на старте, а не поднимается с подставным секретом

### Requirement: Обязательная интерполяция секретов в compose
`docker-compose.yml` SHALL использовать `${VAR:?...}` для секретов, чтобы отсутствующая переменная останавливала запуск, а не подставляла дефолт.

Для `MONGODB_URL`, `JWT_SECRET` и `NUXT_SESSION_SECRET` это уже сделано. Остались дефолты у `S3_ACCESS_KEY`/`S3_SECRET_KEY` (`minioadmin`) и `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` (`test`). Сервис `worker` объявляет тот же набор переменных и MUST быть приведён вместе с `backend`.

#### Scenario: Compose без секрета
- **WHEN** оператор запускает стек без переменной, помеченной как обязательная
- **THEN** compose останавливается с сообщением о недостающей переменной и не стартует контейнеры

### Requirement: Единственный файл окружения и изоляция от сборки
Рабочим файлом окружения SHALL быть `.env.local`; общий `.env` с кредами внешних сервисов удалён вместе с привязкой к внешней инфраструктуре. Файлы-примеры (`.env.example`, `.env.local.example`) MUST содержать только значения локальных контейнеров и плейсхолдеры секретов.

Сборка фронтенда MUST NOT полагаться на файл окружения в репозитории: значения для сборки приходят из окружения сборщика, рантайм-секреты — из окружения контейнера. Плейсхолдер `NUXT_SESSION_SECRET`, которым сборка проходит валидацию схемы, MUST приводить к отказу на старте сервера, если он дожил до рантайма.

#### Scenario: Сборка без файлов окружения
- **WHEN** фронтенд собирается на машине, где файлов окружения нет
- **THEN** сборка проходит на значениях из окружения сборщика, секреты в бандл не попадают

#### Scenario: Плейсхолдер дожил до рантайма
- **WHEN** Nitro-сервер стартует со сборочным плейсхолдером в `NUXT_SESSION_SECRET`
- **THEN** сервер падает на старте с явным сообщением, а не работает с предсказуемым секретом сессии

### Requirement: Схема для LOG_COLLECTOR_URL
Если `LOG_COLLECTOR_URL` задан, он SHALL требовать `https://`. По этому адресу уходят записи логов, включая те, что содержат адреса пользователей, — отправка по HTTP выносит их в открытый канал.

#### Scenario: HTTP-приёмник отклонён
- **WHEN** задан `LOG_COLLECTOR_URL` со схемой `http://`
- **THEN** процесс падает на старте с сообщением о требовании HTTPS
