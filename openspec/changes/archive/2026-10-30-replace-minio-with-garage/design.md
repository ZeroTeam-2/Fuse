## Context

Мотивация — в `proposal.md` (Why). Требования — в `specs/local-dev-environment/spec.md`.

Что важно для выбора подхода:

- **Поверхность замены узкая.** Бэкенд ходит в S3 через один класс (`apps/backend/src/minio/minio.service.ts`) и использует только put/get/remove, `bucketExists`/`makeBucket`, presigned GET и полный multipart-набор. Клиентом остаётся npm-пакет `minio` — он работает с любым S3-совместимым эндпоинтом, менять его не требуется.
- **Прод на MinIO никогда не был.** `S3_URL` в бою указывает на внешний S3 Timeweb (`s3.twcstorage.ru`), MinIO в докере был исключительно локальной заглушкой. Поэтому «локальное хранилище должно совпадать с продовым» — ложное ограничение: его и так не было.
- **Откатиться некуда.** Образ MinIO удалён из реестра, поэтому «вернуть как было» — не вариант восстановления. Любое решение должно быть самодостаточным.
- **Текущие значения в compose захардкожены намеренно.** В шапке `docker-compose.dev.yml` зафиксировано, почему креды локальной инфраструктуры не берутся из `${...}`: compose подхватывает корневой `.env` с боевыми значениями, и при интерполяции локальный MinIO поднимался с прод-ключами и прод-именем бакета. Новый сервис обязан следовать тому же правилу.

Проверено на момент написания: `dxflrs/garage:v2.5.0` тянется анонимно (HTTP 200); все теги `minio/minio` и `minio/mc` отдают 401, `quay.io/minio/*` — тоже; `mongo:7`, `localstack/localstack:4.7.0`, `mccutchen/go-httpbin:v2.15.0` живы.

## Goals / Non-Goals

**Goals:**

- `pnpm infra` поднимается с нуля на чистой машине без `docker login`.
- Сократить локальную инфраструктуру: один контейнер хранилища вместо «сервер + одноразовый бутстрап-контейнер + шелл-скрипт».
- Не менять логику бэкенда — замена должна быть прозрачной для приложения. Правятся только литералы-дефолты кредов (см. решение 8).
- Оставить приёмку проверяемой существующими средствами (`pnpm test:infra`).

**Non-Goals:**

- Переименование `MinioService`/`MinioModule`/`minio.service.ts` во что-то вендор-нейтральное. Переименование тронет 8+ файлов ради косметики и размоет диф этого изменения; выносится в отдельную задачу.
- Замена npm-клиента `minio` на `@aws-sdk/client-s3`.
- Что-либо в `docker-compose.yml` (полный стек) и в проде.
- Возврат админ-веб-консоли для локального хранилища (см. Open Questions).

## Decisions

### Решение 1: Garage, а не bitnamilegacy/minio, LocalStack S3 или SeaweedFS

Выбран `dxflrs/garage:v2.5.0`.

- **`bitnamilegacy/minio`** — образ тянется, и правка была бы минимальной по смыслу. Отклонён: namespace `bitnamilegacy` — замороженная витрина после ухода Bitnami из публичных образов, обновлений там не будет, а сам MinIO-апстрим архивирован, так что мы бы сознательно закрепились на неподдерживаемом сервере. Плюс у Bitnami другой entrypoint, запуск не от root и другой путь данных — «drop-in» всё равно не выходит.
- **S3 в уже работающем LocalStack** (добавить `s3` в `SERVICES`) — заманчиво, минус целый контейнер. Отклонён: связывает доступность хранилища с жизненным циклом SQS-контейнера (падает или ресетится один — уезжает и второе), а LocalStack — эмулятор, а не хранилище: его S3 не предназначен для долгоживущих локальных данных.
- **SeaweedFS** — сопоставим по простоте. Отклонён по сумме: у Garage есть явная таблица S3-совместимости, где все нужные нам эндпоинты (CreateBucket, presigned, весь multipart) помечены как реализованные, и есть штатный однонодовый режим.

### Решение 2: `--single-node --default-bucket` вместо CLI-бутстрапа

Garage начиная с 2.3.0 умеет `garage server --single-node --default-bucket`: сам инициализирует однонодовый кластер и заводит ключ и бакет из `GARAGE_DEFAULT_ACCESS_KEY` / `GARAGE_DEFAULT_SECRET_KEY` / `GARAGE_DEFAULT_BUCKET`.

Альтернатива — классический путь (`garage layout assign` → `garage layout apply` → `garage key import` → `garage bucket create` → `garage bucket allow`) в init-контейнере. Отклонена: это ровно та конструкция, от которой мы уходим (`minio-init` плюс скрипт), только из пяти шагов вместо двух. Штатный режим позволяет удалить сервис `minio-init` и `docker/minio/init-bucket.sh` целиком и делает `pnpm infra` одной командой вместо `up && run --rm`.

Цена — привязка к версии не ниже 2.3.0, поэтому тег пинится явно (`v2.5.0`); `latest` у `dxflrs/garage` не публикуется в принципе.

### Решение 3: порт публикуется как `9000:3900`

S3 API Garage слушает 3900. Маппим на хостовой 9000, который приложение уже знает. Альтернатива — поменять `S3_PORT` в `.env.local.example` на 3900: отклонена, потому что требует синхронной правки у всех разработчиков в их локальных `.env.local` (файл git-игнорируется, автоматически не обновится) и сломала бы дефолты `S3_PORT ?? 9000` в `minio.service.ts` и в infra-смоук-тесте.

### Решение 4: `s3_region = "us-east-1"` в `garage.toml`

Garage обслуживает ровно один регион и отвечает `AuthorizationHeaderMalformed` на запросы к любому другому. Клиент в `minio.service.ts` регион явно не задаёт. Ставим регион, совпадающий с дефолтом клиента, вместо примерного `"garage"` из документации — так вопрос снимается независимо от того, полагается клиент на автодискавери или на дефолт.

### Решение 5: конфиг файлом, значения захардкожены

`docker/garage/garage.toml` монтируется в `/etc/garage.toml` — по тому же образцу, что уже применён для `docker/localstack/init-sqs.sh`. Ключ и секрет (`minioadmin`/`minioadmin`) и имя бакета (`fuse`) задаются литералами в compose, без `${...}`, по причине, зафиксированной в шапке `docker-compose.dev.yml`. `rpc_secret` — фиксированная строка в конфиге: это локальная однонодовая инсталляция, межнодового трафика нет, а генерация на лету потребовала бы entrypoint-скрипта, то есть вернула бы только что удалённый шаг бутстрапа.

### Решение 6: healthcheck средствами самого Garage

`mc ready local` уходит вместе с `minio/mc`. **Проверено на образе**: в `dxflrs/garage:v2.5.0` нет `/bin/sh` вообще (`exec: "/bin/sh": stat /bin/sh: no such file or directory`), entrypoint пустой, cmd — `["/garage","server"]`. Значит форма `CMD-SHELL` неприменима в принципе, healthcheck пишется только в exec-форме на бинаре `garage`; `/garage status` отвечает корректно и годится. Это обязательное условие: `pnpm infra` идёт с `--wait` и без рабочего healthcheck завершится раньше, чем хранилище готово.

### Решение 7: тома пересоздаются, данные не мигрируются

`fuse-minio-data` заменяется на `fuse-garage-meta` и `fuse-garage-data` (Garage хранит метаданные и данные раздельно). Содержимое старого тома не переносится: это локальные тестовые файлы разработчика, их воспроизводит `pnpm seed`. Старый том останется на машинах висеть — его удаление выносится в инструкцию в README, а не в автоматику, чтобы compose-файл не сносил чужие тома.

### Решение 8: `S3_SECRET_KEY` меняется на значение длиной ≥ 16 символов

**Найдено при реализации, не на этапе планирования.** Garage отказывается стартовать с `--default-access-key`, если секрет короче 16 символов: `Error: Invalid default access key: Secret keys should be at least 16 characters long`. Текущий секрет — `minioadmin`, это 10 символов.

Идентификатор ключа Garage принимает любой, поэтому `S3_ACCESS_KEY=minioadmin` остаётся как есть — меняется только секрет, на `fuse-local-dev-secret`. Переименование идентификатора в вендор-нейтральный пошло бы в ту же категорию косметики, что и переименование `MinioService` (см. Non-Goals), и увеличило бы число мест, которые надо держать синхронными.

Альтернатива — не использовать `--default-access-key`, а заводить ключ через `garage key import` в init-контейнере. Отклонена: возвращает удалённый в решении 2 бутстрап-контейнер ради сохранения 10-символьного пароля, причём проверка длины, скорее всего, применяется и там.

Последствие, которого не было в исходном плане: значение прописано в восьми местах, и все они обязаны остаться согласованными, иначе разработчик без `.env.local` молча свалится на старый дефолт и получит ошибку подписи вместо внятного сообщения. Правятся `.env.local.example`, `.env.example`, `docker-compose.dev.yml`, `README.md`, а также литералы-дефолты в `apps/backend/src/config/env.schema.ts`, `apps/backend/src/minio/minio.service.ts` и `apps/backend/test/infra-smoke.infra-spec.ts`. Логика при этом не меняется. `docker-compose.yml` (полный стек) не трогаем: там S3 внешний, а `${S3_SECRET_KEY:-minioadmin}` — плейсхолдер под креды извне.

**Стоимость для команды**: `.env.local` лежит в `.gitignore` и сам не обновится — каждому разработчику нужно поправить в нём одну строку. Это выносится в README и в сообщение PR.

## Risks / Trade-offs

- **Регион и подпись: клиент не договорится с Garage** → **снято проверкой**. Прогон клиента `minio` против `dxflrs/garage:v2.5.0` с `s3_region = "us-east-1"` прошёл зелёным по всем шести операциям, которые использует бэкенд: `bucketExists`, put/get round-trip, `presignedGetObject` (HTTP 200), multipart 2×6 МиБ, `abortMultipartUpload`, `removeObject`.
- **Multipart: ограничения на размер части** → **снято проверкой** там же: части по 6 МиБ собираются в объект ожидаемого размера. Поведение на частях меньше 5 МиБ не проверялось, но `uploads.service.ts` таких и не формирует.
- **Рассинхрон нового секрета между восемью местами** → ловится тем же `pnpm test:infra`: он берёт `S3_SECRET_KEY` из окружения с фолбэком на литерал, так что расхождение между тестом и compose даёт красный тест, а не тихую деградацию.
- **Healthcheck подобран неверно, `--wait` пропускает неготовое хранилище** → падает уже `pnpm seed` или бэкенд, с невнятной ошибкой. Команда проверяется на живом контейнере, приёмка включает полный `pnpm infra:reset` с нуля.
- **Пропажа веб-консоли на :9001** → осознанная потеря; альтернатива — `aws-cli`/`rclone` и Open Questions. Для типового вопроса «лёг ли файл» достаточно `pnpm test:infra`.
- **Отката на MinIO нет.** Revert коммита возвращает в состояние, которое не работает ни у кого. Поэтому изменение вливается только после того, как `pnpm infra:reset` прошёл с нуля на чистых томах, а не «поправим в следующем PR».
- **Garage — тоже внешняя зависимость, которая однажды может исчезнуть.** Снижается пином версии; в отличие от MinIO проект не архивирован и образ публичный. Урок инцидента — не полагаться на `latest` ни для одного образа — вынесен в спеку отдельным сценарием.

## Migration Plan

1. `pnpm infra:down` — остановить текущую инфраструктуру (у большинства она и так не поднимается).
2. Влить изменение, выполнить `docker compose -f docker-compose.dev.yml down -v` для удаления `fuse-minio-data`.
3. **Поправить `S3_SECRET_KEY` в своём `.env.local`** на новое значение из `.env.local.example` — файл в `.gitignore` и сам не обновится (решение 8). Без этого бэкенд получит ошибку подписи.
4. `pnpm infra` — поднимается Garage, бакет создаётся штатным режимом.
5. `pnpm test:infra` — бакет существует, round-trip объекта проходит.
6. `pnpm seed` плюс загрузка файла через UI — проверка presigned GET и multipart на реальном пути приложения.

Откат: см. Risks — отката на MinIO не существует. Если Garage не заработает, следующий кандидат — SeaweedFS, при тех же спеках и той же форме изменения.

## Open Questions

- Нужен ли команде отдельный веб-UI для локального бакета (сторонний garage-webui отдельным контейнером)? Решается после того, как станет понятно, мешает ли отсутствие консоли на практике; на спеки, подход и разбивку задач не влияет.
