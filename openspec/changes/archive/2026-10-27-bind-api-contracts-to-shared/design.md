# bind-api-contracts-to-shared — design

## Context

См. `proposal.md` — Why. Для подхода важны три факта о текущем состоянии:

- `ValidationPipe` уже глобальный (`apps/backend/src/main.ts:17`) с
  `whitelist: true`, `forbidNonWhitelisted: true`, `transform: true`. Чтобы
  тело проверялось, ничего настраивать не нужно — нужен метатип-класс вместо
  литерального типа.
- `packages/shared` — пакет только типов: в `dependencies` нет рантайма, его
  потребляет и браузерный бандл фронтенда.
- `apps/frontend/src/types/api.ts` генерируется из swagger-схемы живого
  бэкенда (`pnpm gen:types`), то есть форма тел в типах фронта — следствие
  DTO бэкенда, а не независимый источник.

## Goals / Non-Goals

**Goals:**

- Расхождение контракта между shared и бэкендом ловится на `typecheck`, а не в
  рантайме и не глазами на ревью.
- Все эндпоинты с телом валидируются одинаково, без исключений.
- Форма тела публикуется в swagger именованной схемой, пригодной для
  `pnpm gen:types`.

**Non-Goals:**

- Нестед-валидация структуры шагов и блоков страницы в `class-validator`.
  Содержимое `steps[]` и `data` проверяют существующие
  `assertValidPageSteps`/`validatePage` на стороне сервиса; переносить это в
  декораторы — отдельная работа.
- Ограничение объёма тела (`inputs`, `data`) — лимиты размера живут в
  `file-size-limits` и к этому change не относятся.
- Единая обёртка ответов (`{ data, error }`). Удаляемые `ApiResponse` и
  `ApiErrorResponse` были заделом под неё; вводить обёртку сейчас не входит в
  объём, и API продолжает отдавать документы напрямую.

## Decisions

**Направление привязки: класс бэкенда `implements` интерфейс shared.**
Интерфейс остаётся объявлением формы, класс добавляет к ней правила проверки и
swagger-описание. Альтернатива «положить DTO-классы в shared и наследовать» —
отвергнута: это тянет `class-validator` и `class-transformer` в пакет, который
попадает в браузерный бандл, и заставляет фронтенд собирать декораторы ради
трёх форм. Альтернатива «генерировать интерфейсы из классов» — отвергнута:
источником правды становится бэкенд, а фронтенд всё равно получает типы из
swagger, то есть генерация дублирует `gen:types`.

**Новые DTO-классы лежат в `apps/backend/src/execution/dto/`,** по файлу на
эндпоинт, рядом с существующим `runs-list-query.dto.ts` — так же, как в
остальных модулях бэкенда.

**`PageSubmitDto` — отдельный тип, не переиспользование `SubmitInputsDto`.**
Формы похожи (`{ stepIndex, data }` против `{ stepIndex, values }`), но это
разные ручки с разной семантикой полезной нагрузки: данные блоков страницы
против значений ручных входов. Один тип на две ручки скрыл бы это различие и
сломался бы при первом же расхождении.

**Без приведения типов в телах.** В query-DTO `@Type(() => Number)` необходим —
query-параметры приходят строками. В JSON-теле число приходит числом, поэтому
`stepIndex` описывается `@IsInt() @Min(0)` без `@Type`: приведение `"0" → 0`
прятало бы ошибку клиента, которую спека требует отклонять (см.
`specs/scenario-execution/spec.md`, сценарий «Неверный тип в сабмите
страницы»).

**`UpdateScenarioDto.steps`: `unknown[]` → `Step[]`.** Альтернатива
`implements Omit<UpdateScenarioDto, "steps">` отвергнута: `Omit` прячет ровно
то расхождение, ради которого затевается привязка. Сужение типа не добавляет
рантайм-проверок — `scenarios.service.ts` уже шесть раз утверждал то же самое
через `as Step[]`; после правки утверждение переезжает на границу API, а
приведения исчезают. Рантайм-контроль структуры шага остаётся прежним
(`assertValidPageSteps`, `cycle-guard`).

**`data` и `values` описываются как `@IsObject()`.** Их содержимое зависит от
сценария и страницы, поэтому проверять его декораторами нечем; задача
валидации тела здесь — отсечь мусор в конверте и не пропустить неизвестные
поля внутрь `Run`.

**Четыре неиспользуемых типа удаляются, а не помечаются `@deprecated`.**
`@deprecated` оставляет их в автодополнении и в графе кода как контракт,
которого нет ни на одной стороне; история правок сохраняется в git, вернуть
тип дешевле, чем годами объяснять его присутствие.

## Risks / Trade-offs

- **Внешний клиент, посылавший лишние поля, получит `400`** → у платформы нет
  внешних потребителей API, кроме собственного фронтенда, а он лишних полей не
  посылает; изменение помечено **BREAKING** в proposal, и после
  `pnpm gen:types` типы фронта отражают новый контракт.
- **Сужение `steps` до `Step[]` может потянуть правки за пределы сервиса**
  (например, в тестах, которые кладут частичные шаги) → `pnpm typecheck`
  покажет полный список до коммита; если объём окажется больше ожидаемого,
  откат к `implements Omit<UpdateScenarioDto, "steps">` с явным TODO — одна
  строка, остальная часть change от этого не зависит.
- **Привязка `implements` защищает только от расхождения формы, не смысла**
  → одинаковая форма с разным смыслом полей по-прежнему возможна; против этого
  работает только ревью спеки.
- **Swagger-схемы переименуются** (инлайн-тела станут `CreateRunDto`,
  `PageSubmitDto`, `SubmitInputsDto`) → `apps/frontend/src/types/api.ts`
  обязателен к перегенерации в этом же change, иначе фронтенд останется на
  старых инлайн-типах и правка форм разъедется незамеченной.

## Migration Plan

1. `packages/shared`: добавить `PageSubmitDto`, удалить `ApiResponse`,
   `ApiErrorResponse`, `ClientWsEvent`, `NotificationsServerEvent`.
2. Бэкенд: три новых DTO-класса, подписи в `execution.controller.ts`,
   `implements` на пяти существующих классах, снятие `as Step[]`.
3. `pnpm typecheck` — зелёный на всех пакетах.
4. Поднять бэкенд и перегенерировать типы фронта: `pnpm gen:types`.
5. `pnpm test` и `pnpm --filter @fuse/frontend typecheck`.

Откат — ревёрт коммита: swagger возвращается к инлайн-телам, валидация трёх
эндпоинтов снимается, удалённые типы возвращаются вместе с файлом. Миграции
данных нет, состояние в БД не затрагивается.
