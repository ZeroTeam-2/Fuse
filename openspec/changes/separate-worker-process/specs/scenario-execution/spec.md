# scenario-execution — delta

## MODIFIED Requirements

### Requirement: Очередь исполнения и архитектура main/worker

Система SHALL исполнять сценарии через очередь задач (SQS-совместимая очередь: LocalStack в деве, облачная в проде) по архитектуре «API-процесс + отдельные воркер-процессы». API-процесс создаёт документ `Run` со статусом `pending` и отправляет сообщение `{runId}` в очередь; воркер-процесс забирает сообщение, исполняет шаги и сохраняет промежуточное состояние (результаты шагов, тайминги) в документ `Run` после каждого шага.

Воркер MUST быть самостоятельным процессом с собственным entrypoint: API-процесс MUST NOT потреблять очередь, воркер-процесс MUST NOT поднимать HTTP-сервер. Оба процесса собираются из одной кодовой базы `@fuse/backend` без дублирования логики исполнения.

Система SHALL поддерживать одновременную работу нескольких воркер-процессов на одной очереди: распределение сообщений между ними обеспечивается семантикой SQS (visibility timeout), координация между воркерами в коде MUST NOT требоваться. Число одновременно исполняемых запусков внутри одного воркера SHALL задаваться переменной окружения `WORKER_CONCURRENCY` (границы 1–10 — лимит выборки SQS; значение по умолчанию 5).

При падении воркера сообщение возвращается в очередь по истечении visibility timeout, и другой (или перезапущенный) воркер загружает промежуточное состояние из `Run` и продолжает с последнего сохранённого шага. Система SHALL поддерживать статусы `Run`: `pending`, `running`, `waiting_input`, `completed`, `failed`, `cancelled`.

#### Scenario: Создание задачи на исполнение

- **WHEN** пользователь запускает сценарий
- **THEN** API-процесс создаёт `Run` со статусом `pending`, отправляет сообщение в очередь и возвращает `runId` для подключения к WebSocket

#### Scenario: API-процесс не исполняет запуски

- **WHEN** запущен только API-процесс (без единого воркера) и пользователь запускает сценарий
- **THEN** сообщение остаётся в очереди, `Run` остаётся в `pending`, а API продолжает обслуживать HTTP и WebSocket; после старта воркера накопившиеся сообщения обрабатываются

#### Scenario: Несколько воркеров делят одну очередь

- **WHEN** запущено N воркер-процессов и в очередь отправлено M сообщений
- **THEN** каждое сообщение обрабатывается ровно одним воркером (в пределах гарантий at-least-once с идемпотентной записью результатов), запуски исполняются параллельно на нескольких процессах

#### Scenario: Параллелизм воркера конфигурируем

- **WHEN** воркер запущен с `WORKER_CONCURRENCY=10`
- **THEN** воркер обрабатывает до 10 запусков одновременно; без переменной — 5

#### Scenario: Восстановление после падения worker'а

- **WHEN** воркер падает на шаге K из N
- **THEN** сообщение возвращается в очередь по visibility timeout, следующий получивший его воркер загружает промежуточное состояние из `Run` и продолжает с шага K без потери выполненных шагов

#### Scenario: Успешный запуск потока

- **WHEN** воркер исполняет N шагов с валидными входами
- **THEN** система выполняет все шаги по порядку, передавая данные по маппингу, сохраняет результаты каждого шага в `Run` и возвращает итоговый результат с суммарным временем

#### Scenario: Ошибка стороннего API

- **WHEN** endpoint шага возвращает ошибку
- **THEN** `Run` переходит в статус `failed`, пользователь видит на каком шаге и какая ошибка произошла

### Requirement: Real-time прогресс через WebSocket

Система SHALL предоставлять real-time обновления прогресса выполнения сценария через WebSocket-соединение по `runId`. Воркер публикует события (`step:start`, `step:done`, `page:required`, `input:required`, `progress`, `run:done`, `run:error`, `run:status`) в комнату запуска; клиент, подписанный на `runId`, получает их немедленно.

Клиентские сокеты подключены к API-процессу, а воркер исполняется отдельным процессом, поэтому события воркера MUST доставляться в API-процесс через межпроцессный канал поверх MongoDB (публикация конвертов воркером, чтение и трансляция в socket.io-комнаты API-процессом). Прямой вызов гейтвея в памяти допустим только для событий, порождаемых самим API-процессом (отмена, сабмит). Канал MUST работать на standalone MongoDB (без требования replica set). Уведомления (`notification:new` в комнату пользователя) доставляются тем же каналом.

Канал доставляет «живость», а не истину: состояние `Run` MUST быть сохранено в MongoDB до публикации события, чтобы потеря события в канале компенсировалась снапшотом. При подключении клиента к `runId` сервер MUST немедленно отправить этому клиенту снапшот текущего состояния `Run` (статус, `currentStep`, накопленные `stepResults`, текст ошибки при наличии) — до и независимо от последующих инкрементальных событий. Клиент, подключившийся после начала исполнения (в том числе после завершения запуска, после реконнекта или перезагрузки страницы), MUST получить актуальное состояние и MUST NOT остаться без обратной связи из-за событий, отправленных до его входа в комнату.

#### Scenario: Событие воркера доходит до клиента API-процесса

- **WHEN** воркер, исполняющийся отдельным процессом, публикует `step:done` для запуска, на который подписан клиент, подключённый сокетом к API-процессу
- **THEN** клиент получает событие через WebSocket с задержкой, незаметной пользователю (без ручного обновления страницы)

#### Scenario: Уведомление из воркера доходит до колокольчика

- **WHEN** воркер завершает запуск (или переводит его в `waiting_input`) и создаёт уведомление владельцу
- **THEN** событие `notification:new` доходит через межпроцессный канал до клиента владельца, подключённого к API-процессу, и счётчик колокольчика обновляется без перезагрузки

#### Scenario: Подключение после старта исполнения

- **WHEN** воркер начал (и, возможно, уже завершил) исполнение до того, как клиент подключился к `runId`
- **THEN** клиент при подключении получает снапшот с текущим статусом и результатами шагов и отображает актуальное состояние вместо бесконечного «Выполняем сценарий…»

#### Scenario: Быстрый запуск завершился до подключения

- **WHEN** запуск падает или завершается за миллисекунды — раньше, чем браузер успел открыть WebSocket
- **THEN** клиент при подключении получает снапшот со статусом `failed` (с текстом ошибки) либо `completed` (с результатами) и показывает соответствующий экран

#### Scenario: Reconnect после обрыва WebSocket

- **WHEN** WebSocket-соединение обрывается во время выполнения
- **THEN** клиент переподключается по `runId`, получает снапшот текущего статуса и результаты выполненных шагов без потери прогресса

#### Scenario: Кратковременный сбой межпроцессного канала не искажает состояние

- **WHEN** канал доставки событий между воркером и API временно недоступен, пока запуск продолжает исполняться
- **THEN** состояние `Run` в MongoDB продолжает обновляться, и клиент после реконнекта (снапшот) видит актуальные статус и результаты шагов
