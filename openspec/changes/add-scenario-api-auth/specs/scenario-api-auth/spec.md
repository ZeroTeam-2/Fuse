## ADDED Requirements

### Requirement: Ключи доступа к API на уровне сценария
Система SHALL хранить на сценарии набор ключей доступа к внешним API — по одной записи на каждого поставщика (`appId`), задействованного в шагах. Запись MUST включать имя HTTP-заголовка, формат значения (`bearer` — префикс `Bearer `, или `raw` — как есть) и секретное значение. Список поставщиков на вкладке «Авторизация» MUST быть производным от шагов сценария (как на вкладке «Окружения»): поставщик появляется с первым api/periodic-шагом и исчезает, когда таких шагов не остаётся; при сохранении система MUST удалять ключи поставщиков, которых больше нет в шагах.

#### Scenario: Сохранение ключа для поставщика
- **WHEN** владелец на вкладке «Авторизация» задаёт для поставщика заголовок `Authorization`, формат Bearer и токен, и сохраняет
- **THEN** система записывает ключ в сценарий и при последующих запусках использует его для шагов этого поставщика

#### Scenario: Поставщик появляется из шагов
- **WHEN** пользователь добавляет первый api-шаг по новому поставщику
- **THEN** на вкладке «Авторизация» появляется карточка этого поставщика

#### Scenario: Ключ удаляется вместе с поставщиком
- **WHEN** пользователь удаляет все шаги поставщика и сохраняет сценарий
- **THEN** запись ключа этого поставщика больше не хранится в сценарии

### Requirement: Видимость ключа только владельцу
Значение ключа (`value`) MUST быть доступно в API и UI только владельцу сценария. Для любого другого аутентифицированного пользователя и для публичных представлений опубликованного сценария система MUST NOT возвращать `value`; при этом система MAY сообщать факт наличия настроенного ключа (`configured: true/false`) без раскрытия секрета. Любой пользователь, имеющий право запустить сценарий, MUST получать исполнение с ключом владельца (инжект на сервере), не видя значения.

#### Scenario: Владелец видит значение
- **WHEN** владелец открывает вкладку «Авторизация»
- **THEN** система показывает сохранённое значение ключа (с возможностью скрыть/показать в поле)

#### Scenario: Чужой не видит значение
- **WHEN** не-владелец получает представление сценария через API
- **THEN** в ответе нет поля `value` у записей auth, даже если ключ настроен

#### Scenario: Чужой запуск использует ключ владельца
- **WHEN** аутентифицированный не-владелец запускает опубликованный сценарий с настроенным ключом
- **THEN** worker подставляет ключ владельца в HTTP-запрос, а клиент запускающего не получает значение ключа

### Requirement: Вкладка «Авторизация» в редакторе
Редактор сценария SHALL иметь вкладку **«Авторизация»** наряду с «Основная», «Настройка шагов» и «Окружения». На вкладке — по одной карточке на поставщика: выбор поля заголовка (`Authorization`, `X-Api-Key` или свой), значение ключа в секретом поле с переключателем видимости, подсказка вида «передаётся как `Header: •••`». Пока в сценарии нет поставщиков из шагов, вкладка MUST показывать пустое состояние с предложением сначала добавить шаг.

#### Scenario: Пустое состояние без шагов
- **WHEN** в сценарии ещё нет api/periodic-шагов и владелец открывает «Авторизацию»
- **THEN** система показывает пустое состояние с пояснением добавить шаг

#### Scenario: Карточка с дефолтом из App
- **WHEN** у поставщика при импорте сохранён auth hint Bearer
- **THEN** новая карточка на вкладке по умолчанию предлагает заголовок `Authorization` и формат Bearer

### Requirement: Переключатель auth на шаге
У шагов типа api и periodic система SHALL хранить флаг `authEnabled`. Панель настройки шага MUST показывать секцию «Аутентификация»: если ключ поставщика настроен — тоггл вкл/выкл; если не настроен — предупреждение перейти на вкладку «Авторизация» и тоггл недоступен; если у сервиса нет auth hint и ключ не задан — сообщение, что сервис не требует аутентификации (пользователь MAY всё же задать ключ на вкладке и включить тоггл). Карточка шага в списке MUST показывать индикатор (shield), когда `authEnabled` истинен.

При добавлении шага `authEnabled` MUST по умолчанию быть `true`, если у приложения есть auth hint, иначе `false`.

#### Scenario: Тоггл при настроенном ключе
- **WHEN** ключ поставщика сохранён и владелец выключает «Аутентификация» на шаге
- **THEN** при исполнении этого шага система не инжектит ключ из authConfig

#### Scenario: Предупреждение без ключа
- **WHEN** у шага `authEnabled` по умолчанию включён, но ключ на вкладке не задан
- **THEN** панель шага показывает предупреждение настроить авторизацию, а тоггл нельзя включить осмысленно до появления ключа (или остаётся выключенным/disabled до настройки)

### Requirement: Хранение plaintext и отсутствие секретов в логах
Система MAY хранить значения ключей в хранилище в открытом виде (plaintext). Система MUST NOT записывать значения ключей и итоговые auth-заголовки в результаты шагов запуска (`stepResults`), тексты доменных ошибок, отдаваемые клиенту, и структурированные логи исполнения.

#### Scenario: Результат шага без секрета
- **WHEN** worker успешно вызывает API с инжектированным Bearer-токеном
- **THEN** в `stepResults` и событиях прогресса нет значения токена и заголовка Authorization
